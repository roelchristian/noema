# External AI security architecture — D02A

Noema external AI is an opt-in application security boundary. Apple Intelligence remains independent: saving, title inference, LCC classification, page creation and source processing never silently fall back to cloud inference. D02A does not encrypt the plaintext vault or provide cryptographic vault locking.

## Trust and module boundary

`noema` owns explicit UI actions, consent, selected-item snapshots and publication through existing repositories. `ExternalAI` owns typed contracts, `ExternalAICredentialBroker`, `ExternalAISessionManager`, `ExternalAIGateway` and its restricted `OpenAITransport`. It depends on `VaultCore` for the existing D02 access gate, session lease and admission/completion boundaries, and on `NativeAuthentication` for operation-specific native authentication attempts. Credentials remain entirely inside the security module after masked entry. General app state obtains credential status and approved action results only.

The trusted callers are explicit provider-routed page/source enrichment, title-suggestion and reviewed page-composition UI actions and the credential settings action. Provider defaults and action preferences never grant submission consent or session authorization. Source processing and automatic inference cannot call OpenAI. Caller-provided identity or a constructed consent receipt alone does not grant authorization. Gateway validation checks the live D02 lease, an issued authorization capability, and single-use per-submission consent. There is no generic prompt, arbitrary URL, tool execution, background cloud action or whole-vault submission API.

This beta implementation shares a process with UI code. Swift access control, actors, opaque capabilities and Keychain reduce accidental disclosure and ordinary caller misuse; they cannot protect secrets from arbitrary malicious code executing in that process. Debuggers, memory dumps, compromised dependencies and deliberately misused trusted callers remain risks. Do not claim otherwise.

A future dedicated XPC service can own Keychain, authentication, capability validation and restricted transport behind the same closed operation set. IPC must independently validate caller identity and operation limits; merely moving an arbitrary-text summarizer to XPC does not prevent compromised authorized callers from substituting text. Higher assurance requires an independently trusted content broker and authenticated vault/session authority.

## Operation inventory and exfiltration policy

| Operation | Approved source | Authority and destination | Limit and cancellation |
| --- | --- | --- | --- |
| `summarizePage` | Text snapshot of one explicitly selected page | Exact vault UUID, session UUID and generation; result returned only to that original page/request/revision | 64 KiB UTF-8 content; 8 KiB summary; 128 KiB response body; caller Task cancellation and lifecycle revocation |
| `summarizeSource` | Available extracted text snapshot of one explicitly selected source | Exact vault UUID, session UUID and generation; result returned only to that original source/request/revision | Same limits and cancellation |

Summary operations use one strict structured result containing required nullable `title`, `classification`, and `body` fields plus a nonempty `summary`. Initial enrichment may supply an unset title; regeneration preserves the established title and body. `composePage` targets a new page UUID and produces a required title and Markdown body, summary and classification in one inference. Its input is selected source extraction, bounded topic research evidence, or locally fetched URL extraction. No model tools, arbitrary instructions, model URL fetching or background cloud inference are exposed. On-device and external composition inputs, selected-source snapshots, proposals and drafts are transient session-owned data under the [classification and lifecycle policy](storage-boundary.md). Published summaries, classifications and provenance become authoritative vault content and follow its preservation rules; activity history has independent metadata retention. Drafts remain transient until explicit review publication; cancellation, refusal, invalid artifacts, stale source snapshots or revoked publication authority cannot create a partial page. Bodies are bounded to 64 KiB; input, summary and response limits remain as in the table. The gateway binds the digest of every artifact and request mode to the publication permit.

Classification is null when unavailable, or exactly `code`/`level`/`rationale`. Only `LCCClassificationVocabulary` entries are accepted. Numeric and decimal entries are exact verified headings from the [2025 Q schedule](https://www.loc.gov/aba/publications/FreeLCC/LCC_Q2025TEXT.pdf); this finite vocabulary is not complete LCC schedule coverage or shelf-mark validation. Unsupported specificity must use a verified subclass or explicit null. Captions and levels resolve locally, never from model captions. Legacy stored/manual values remain readable until a later enrichment replaces them. The Properties inspector is read-only and has no independent classification command. Standalone title suggestion still requires review and collision checks. Compatibility classification APIs remain for existing consumers/tests but are absent from native actions and settings.

`publishPageEnrichment` and `publishSourceEnrichment` conditionally write the summary and classification together, and fill only an empty/Untitled title. Typed classification metadata and artifact provenance share a separately minted generation UUID, never a consent or request UUID. Missing classification clears old generated/manual classification at this explicit enrichment boundary; deleting a summary preserves classification. Ordinary Markdown/frontmatter and source JSON open without rewriting; older provenance remains intact and provider preferences never regenerate saved artifacts.

Transmit only the selected text, a fixed provider-owned action instruction, the fixed enrichment schema when applicable, and configured model. Never transmit vault names, folder paths, UUIDs, revision IDs, file URLs, associated pages, other sources, frontmatter or unrelated metadata. Text itself may contain private information: submission confirmation follows the explicitly selected global policy; its default is Always ask. A credential connection check uses a fixed provider metadata request with no vault content; it is not a general inference path. Its dispatch is serialized with the live credential-version registry, and replacement/removal/expiry cancel its active exchange.

`OpenAIConsentPolicy` is a versioned global preference independent of provider and credential settings. Always ask is the default, including malformed, unsupported-version and absent preferences. Once per session requires exact-text approval for the first explicitly initiated submission in each unlocked vault lease; later explicit actions can mint fresh bound receipts. Never ask skips routine prompts only after explicit Settings selection. Neither policy admits automatic actions or bypasses credentials, authentication, cancellation, model validation or conditional publication. Grants bind vault UUID, session UUID and generation and are synchronously cleared on lock/close/switch; relaunch has no stored grant.

When confirmation is required, the sheet shows provider/model, selected item, exact UTF-8 byte count, external processing/cost and conditional replacement, with Cancel and Send and an exact-text preview. Unauthenticated authority uses expanded disclosure; authenticated authority may use compact disclosure. The app evaluator checks the current unlocked lease and either explicit confirmation or live policy authorization before minting the same single-use request-bound receipt. Consent presentation never replaces gateway authorization.

Consent binds request UUID, target/action/mode, authority, content revision and SHA-256 of the exact content snapshot. Each receipt is consumed once at the gateway; any bounded internal retry belongs to that same approved request. A changed snapshot needs fresh consent even when identifiers are accidentally reused. The consent SHA-256 is local validation state and is never transmitted or persisted. A separate source-content revision may be persisted as artifact provenance; it identifies the content used for generation, never an authorization receipt. Consent is evidence of trusted UI approval, not a cryptographic attestation of user interaction.

Page/source text and provider output are untrusted data. Prompt injection can ask the model to reveal content or act on instructions: fixed action instructions must label submitted text as data; do not expose tools, URLs or external side effects, follow output instructions, or render provider HTML unsafely. Limits and scope constrain disclosure even when the model disobeys. A result cannot authorize another operation; publication identity includes its action.

## Authorization lifecycle contract

States: unauthorized, authorizing, authorized, expired and revoked. Authentication coalesces concurrent prompts for the same precise vault authority. A cancelled, failed or outdated prompt fails closed and must not mint a capability. Production initialization fixes LocalAuthentication, the system clock and native revocation observation; substituted authenticators/clocks/disabled observation are internal test seams. `LocalAuthentication` permits normal macOS authentication fallback when configured; it never replaces explicit content consent.

The native adapter invokes a fresh `NativeAuthentication` attempt for the external-AI authorization purpose, covering explicitly initiated enrichment, title suggestions and reviewed page composition under the selected confirmation policy. Native cancellation maps to the existing authentication-cancelled error; native unavailability and failure map to authentication-failed without exposing platform diagnostic text. Attempt success is not a capability or session: `ExternalAISessionManager` still binds and issues its own authorization after revalidating the precise live vault authority and credential version. Other operation purposes cannot reuse this attempt as vault admission. The credential broker's separate noninteractive Keychain authentication context remains independent of the explicit native prompt.

An authorized capability is opaque, binds vault UUID + D02 session UUID + UInt64 generation and the broker's credential-version UUID, and is validated against its issuing manager's live registry. Comparing a folder path or vault UUID alone is insufficient. Each open/unlock produces a distinct D02 session authority. Only authorized external-AI activity updates the idle timestamp. Default idle expiry is 30 minutes; absolute expiry is four hours from authentication. Custom policy may shorten, never extend, these limits. Ordinary editing, mouse activity and status reads do not renew authorization. Check time on every use, independently of timer delivery.

| Event | Required transition/effect |
| --- | --- |
| First deliberate AI action without a valid capability | Authorizing; authenticate; authorize only if the original open authority remains current |
| Subsequent explicitly approved action within lifetime | Reuse authorization; consume a fresh consent receipt |
| Idle/absolute timeout | Expired; reject further dispatch and publication, cancel outstanding requests |
| Vault locking, closing, switching, or any non-open phase | Revoke immediately; cancel operations; require new authorization even if locking later aborts |
| Sleep, macOS session lock, app termination | Revoke and cancel; next use authenticates again |
| Credential replacement, removal, local expiry or access revocation | Change credential-version UUID, revoke cached capabilities, cancel requests |

Local beta credential expiry may be an optional 30-day policy. It is not actual OpenAI key expiry or a provider spending limit. Provider-side spending limits, key expiry and revocation belong to the issuer.

The broker stores secrets only in a dedicated Keychain item, restricted to the application's signing identity/designated security component without unnecessary sharing entitlements. It must not return raw key strings through public APIs. Session authorization must not accidentally read a biometric-gated Keychain item afresh and reprompt on every summary: coordinate access through the broker's authenticated capability. Store/replacement/removal completes only after invalidating earlier credential authority. Saving also requires a noninteractive readback equal to the exact encoded record before installing new credential authority or reporting success. Successful writes followed by denied, missing or mismatched reads return the finite credential-unavailable error, preserve the Keychain item, and leave prior authority revoked. See [credential broker regression tests](../../Tests/ExternalAITests/ExternalAICredentialBrokerTests.swift).

Keychain implementation is selected once from the running process's code-signing flags. Ad-hoc development bundles use the nonsynchronizing file-based login Keychain with an explicit `SecAccess` ACL trusting only the creating application. Certificate-signed bundles retain the data-protection Keychain and require provisioned app identity entitlements; records use `WhenUnlockedThisDeviceOnly` and disable synchronization. No access-denied operation retries against another Keychain, and unreadable signing metadata fails closed. Changing signing modes does not migrate or delete the other store's record. See [Apple's Keychain implementation guidance](https://developer.apple.com/documentation/technotes/tn3137-on-mac-keychains) and [system adapter regression tests](../../Tests/ExternalAITests/SystemExternalAIKeychainTests.swift).

Credential operations never invoke login-Keychain password dialogs. The file-based implementation ignores SecItem's per-query UI controls, so the native operations use a serialized synchronous scope around `SecKeychainSetUserInteractionAllowed(false)` and restore the previously observed process policy on success or failure. Setup/restoration failures reject without returning credential bytes. This suppresses UI rather than bypassing access control; blocked reads/writes still fail. An ad-hoc rebuild changes signing identity: Settings reports the old credential as inaccessible, and the user can explicitly remove it before saving a fresh item for the new build. A locked Keychain must be unlocked separately in Keychain Access; Noema does not retry with interactive approval. Session LocalAuthentication remains independent. See [interaction-scope tests](../../Tests/ExternalAITests/KeychainInteractionGuardTests.swift).

## Dispatch, transport and publication

Gateway order: validate action and payload; match live gate/session authority; authenticate if needed; validate capability and credential version; validate and consume request-bound consent; admit/register cancellable operation; recheck authority/cancellation at the transport dispatch boundary. Admission must be closed as soon as vault locking starts, including during an authentication await. There must be no stale authorization window between checking state and initiating I/O.

OpenAI requests use only the configured HTTPS OpenAI endpoint with a restricted Responses request shape and `store: false`. Reject cross-host redirects and unexpected response types/statuses; bound bytes while streaming, not only after allocating an unlimited response. Use a 60-second timeout and at most one bounded retry for transient failures, checking cancellation, session, consent operation identity and capability again before any retry. Never retry authentication or permanent request failures automatically. Inject mock transport for tests; tests must not need a real key or live network.

The exact `gpt-6-luna` model uses a saved reasoning effort selected from `none`, `low` and `medium`, defaulting to `low` for new and existing installations. Settings persist the finite effort separately from the validated model; changing either configuration revokes session authorization and replaces the gateway. The selection survives model changes, but the picker is disabled and no reasoning parameter is sent for other model identifiers. Luna retains an 8,192-token generation ceiling at every effort, including reasoning; other models retain the 2,048-token ceiling. These are billing/generation bounds, distinct from the unchanged 8 KiB summary and 128 KiB response byte limits. Completed responses may include reasoning items, which are ignored rather than published. Only completed assistant `output_text` enters action-specific result validation; unexpected operations, absent answers and malformed output still reject. Refusals, unfinished output and generation-limit exhaustion have separate finite errors; partial summaries never receive publication authority and these failures do not trigger automatic retransmission. See [response regression tests](../../Tests/ExternalAITests/OpenAISummaryResponseTests.swift) and [OpenAI reasoning guidance](https://developers.openai.com/api/docs/guides/reasoning).

Return an immutable result retaining request UUID, target, content revision and authority. The gateway retains only bounded publication identity/provenance bindings and a SHA-256 output digest; it does not cache plaintext results after return or across vault locking. Before publication, verify cancellation, current issued capability, live D02 lease/generation, still-existing target, original selection/request identity, exact captured content/revision, and unchanged prior summary. Persist through existing page/source repository mechanisms only when all checks still hold. Independent local summary edits cannot be overwritten. Editor changes and selection changes invalidate a synchronized request predicate, including changes that later return to the original values. The repository checks that predicate and the synchronous publication permit after its final actor hop immediately before conditional persistence. These admission checks do not hold authorization locks across gated storage, which would invert the gate/registry lock order. A synchronous write already admitted before concurrent revocation or editor invalidation can complete; no stale post-await write may be newly admitted. Linked-original rereads and metadata replacement are separate operations, so externally owned original files can still change after the final read. Treat provider text as a complete locally validated enrichment or reviewed title proposal, with provenance (provider, model, generation timestamp, optional local source revision). Preference changes leave saved artifacts untouched and never trigger requests. Failed/cancelled operations preserve the previous artifact. Legacy artifacts without provenance remain readable without fabricated provider facts. Never persist session/capability/consent objects or request content as diagnostics.

Cancellation prevents subsequent dispatch and stale publication. It cannot recall data already delivered to OpenAI; retries can repeat transmission and provider billing. Already sent data remains governed by provider policy. `store: false` disables response persistence according to the [OpenAI Responses documentation](https://developers.openai.com/api/docs/guides/migrate-to-responses); it is not a promise of zero provider retention.

## Composition acquisition limits

URL acquisition reuses `WebSourceFetcher`, its 2 MB streaming bound and 20-second timeout. Initial and redirect destinations must use HTTP(S), no credentials, allowed web ports, public hostnames and globally routed resolved addresses; local/private, loopback, link-local, mapped/transition and documentation addresses are rejected. HTTPS redirects cannot downgrade to HTTP. Ephemeral sessions omit caches, cookies and URL credentials. DNS is checked before each dispatch/redirect but is not pinned to the socket address: DNS rebinding and resolver differences remain a documented limitation, not a guarantee against a hostile network. Tests exercise the address policy without live network access.

Composition keeps source relationships and adds verified topic/URL references locally, outside the model response. URL mode may retain the already fetched capture as a source when publishing; this uses existing import staging. Source import and page creation are separate transactions. If page publication fails after a requested source capture succeeds, that intact source is preserved; there is no partial page and retry must resolve the retained-source collision. Device, accessibility, crash-durability and live-provider acceptance gaps remain as recorded in [validation](../validation.md).

## Diagnostic and validation policy

Errors are a finite typed set with fixed user-facing descriptions. Underlying Keychain/LA errors, request/response bodies, Authorization headers, raw provider error strings, input and output text must not enter logs, crash diagnostics, preferences, journals or public errors. An explicit session-only OpenAI debug mode is the sole response-body inspection exception: Settings may show the latest bounded rejected response and finite failure code in memory for the current unlocked vault. It defaults off, captures no request body or headers, and is disabled and cleared synchronously on vault lock/close/switch. It never writes diagnostic bodies to storage or activity history. Request/result debug representations redact text. Reflection/memory access to live objects still falls within the documented in-process limitation.

### Activity history

The application-level activity database accepts typed operation metadata only: logical operation UUID, UTC timing, optional vault and page/source UUIDs, finite action/provider/execution/status/outcome/failure codes, validated model identifier, duration, optional input byte count, actual cloud dispatch count and provider-reported token usage. It has no title, excerpt, input/output text, arbitrary error, HTTP header/body, credential, consent or access-capability field. Request bodies remain inside the gateway; outside the explicit in-memory debug inspector, only validated numeric usage leaves its response parser. Activity IDs are diagnostic correlation identities, never authorization or publication authority.

One logical operation owns one record, including compound local helper calls and cloud retries. A consent proposal cancelled before transport has zero dispatches. Inference completion and successful publication are separate: title/LCC proposals record `suggested`, later changing to `published` or `rejected` on review. Finalization updates running records once; stale publication and cancellation preserve existing artifacts. Startup reconciles previously running records as interrupted. Storage failures are best effort and must not change inference, authorization, cancellation or publication results. The interface explains this limitation; history is not a tamper-proof audit.

Settings conceals vault and target identity outside the current accessible vault, resolves titles from current in-memory metadata only, and checks the synchronous session gate before navigation. Settings metadata exports omit vault and target identifiers for every vault and never export titles. The application database itself retains plaintext UUIDs and technical metadata across lock/close. Session locking does not encrypt that database; future encrypted-vault support must separately address this copy.

Retention defaults to 90 days, can be changed or disabled, prunes completed records at opening and periodically during recording, and preserves active operations. Clear History requires confirmation and affects every vault's history while leaving saved AI artifacts intact. Export is bounded to 1,000 matching records and creates a new external JSON file; it cannot replace an existing file or write inside captured/current vault and known recovery/activity roots. Native destination selection and symlink-resolved routing checks precede writing. A failed or interrupted external write can leave a partial new file. Pruning and clearing are ordinary deletion, without secure-erasure claims. Optional cost is an estimate from a versioned model/date pricing catalogue and reported input/output/cached token counts. Unknown usage or missing applicable prices remains unknown; local executions do not fabricate tokens or charges. The default catalogue has no assumed prices.

Contract tests cover exact consent snapshots, precise authority identity, UTF-8 limits, bounded summaries, sanitized diagnostic representations and policy ceilings. Broker/session/gateway tests must additionally cover Keychain failures/replacement, authentication coalescing/cancellation, lock races, expiry, sleep/session events, redirect rejection, bounded responses, retries and stale publication. Existing storage guard and native tests remain release gates. Device validation must exercise biometric success, cancellation and permitted macOS fallback; test doubles cannot establish those platform guarantees.


## D02A.7 audit evidence and release gate

The deterministic security tests use synthetic credentials and injected authentication/transport. `OpenAITransportSecurityTests` additionally injects URLProtocol into the actual ephemeral URLSession to exercise redirect cancellation, unexpected response type/URL/status rejection, sanitized platform failures and delegate chunk limits without network. `ExternalAIAdversarialTests` covers connection-validation credential replacement/removal, synchronous credential expiry before dispatch/publication, revocation before retry, cancellation before dispatch, closed-session delayed responses, forged results and revoked publication permits. The session and broker suites cover exact generation, coalesced/pending prompts, deadlines, clock rollback, credential failures/replacement/expiry and synchronous lifecycle cancellation. Application/repository summary tests cover publication, stale content, independent summary edits and selection/session/cancellation races.

Automated results and manual status are recorded in [validation](../validation.md). Hardware Touch ID, permitted password fallback, signed-app Keychain isolation, native sleep/screen-session event delivery and live-provider behavior remain manual release gates; injected doubles cannot establish these guarantees. No claim of completed device/provider validation should be inferred from deterministic test success.
