# Noema architecture

## Canonical storage reconciliation (STOR.01)

The implementation baseline is `890898fbe0d1511e64dd3e41f932be1147bb79b3`,
including EDT.BLK09–14. This is a page-first SQLite implementation with distinct
file-backed source and preservation authorities. Its current boundary is implemented;
the expansion below is a future implementation requirement. Source and tests govern
when older D-series or EDT.BLK proposals disagree with this baseline.

| Surface | Current authority and evidence | Approved target / disposition |
| --- | --- | --- |
| Pages, block documents and page Trash | Format 2 `blocks.sqlite`, schema `user_version=2`; actor-owned `SQLiteBlockStore` and `SQLiteRepositoryTests`. Implemented and verified by the named automated scenarios, subject to [acceptance limits](validation.md#sqlite-storage-acceptance). | Retain relational blocks, opaque revisions and incremental writes; extend the existing store rather than replace it. |
| Source metadata, originals and page references | `Sources/<UUID>/metadata.json` and checksum-verified bytes through `VaultContentStore`; ordered source UUID references are in canonical page metadata. Implemented but limited: separate stores have no compound transaction. | STOR.02 moves structured source metadata and relationships to SQLite only after explicit authority transition; imported originals remain controlled immutable blobs, linked originals externally owned. |
| Conflicts, source Trash and retained legacy page Trash | Repository-owned file preservation and retention ledger. Implemented but limited; SQLite page Trash does not make all preservation metadata database-owned. | Canonical logical Trash, tombstones and conflict disposition become SQLite-owned; unique preserved bytes remain recoverable. |
| Creation and conversion | `VaultCreation` creates Markdown format 1; `SQLiteVaultMigration` implements explicit verified manifest-last page conversion. | STOR.02 changes the eligible local creation default; existing vaults never convert on open. STOR.03 supplies explicit expanded-authority migration and complete restoration verification. |
| Document compatibility | `BlockDocument`/codec retain supported kinds, runs, tree, semantic extension map, source spellings and recovery payload. Bounded opaque optional JSON now round-trips in domain scopes; expanded writable payloads require explicit schema 3. Production schema-3 admission remains closed. | Versioned opaque optional extensions and required-feature rejection are specified in [block-editor.md](contracts/block-editor.md); preservation-only reads grant no save authority. |
| Complete archive and annotations | Live-page Markdown export and SQLite backup exist; neither is a complete archive. Complete archive remains unimplemented; inline annotation domain records and conservative persistence invalidation exist in the explicit staging foundation. | STOR.03 owns complete archive/restore; annotations remain a deferred extension, independent of formatting-run identity. |
| Search, activity and drafts | App-local `SQLiteSearchIndex`, metadata-only `SQLiteAIActivityStore`, and preservation-only `RecoveryStore`. Implemented with different lifecycle rules. | Search/embeddings remain rebuildable; activity is independent history; drafts retain separate preservation authority until explicit commitment/discard. |
| Older “v1 only”, file-only canonical authority and hypothetical SQLite proposals | Contradictory or superseded by format-2 code and SQLite tests at this baseline. | Replace with the present authority map; E-series encryption and device/crash acceptance remain future gates. |

The target keeps manifest format 2 and `storageMode: sqliteBlocks`, but requires a
nested storage declaration with schema version 3 and `canonicalMetadataV1` among
its required capabilities, agreeing with database vault identity/capabilities.
Current clients reject this nested declaration before opening format 2. Table
addition alone never changes existing authority; schema 2 remains page-only.
The [canonical storage decision](decisions/0001-canonical-sqlite-authority.md) and
[versioned ownership contract](contracts/storage-boundary.md) specify the exact
discriminator, integrity rules and explicit migration gate. No runtime
schema, manifest, migration or creation default changes occur in STOR.01.

STOR02A adds an internal explicit schema-3 staging foundation and bounded
versioned JSON preservation in the existing domain/store. Its compound source/page
API admits receipt-verified imported and linked sources in explicitly initialized
canonical repositories. Schema-2-to-3 authority-changing migration and final
acceptance remain incomplete; existing format 1/2 behavior and creation defaults
remain unchanged. See the [current foundation and remaining gates](contracts/storage-boundary.md#canonical-persistence-implementation-stor02a).

## Where things live

The Semantic Blocks library scope derives searchable block rows from page snapshots off the main actor, without a persisted index or schema change. It searches semantic metadata, block text, and owning page titles, omitting generated AI summaries. Selection uses the existing save-before-navigation path and block editor action; ContentView reuses the same article detail and page inspector as Pages. Current editor content is included in search snapshots and debounced edits refresh results.

**VaultCore** is independent of SwiftUI. `FileVaultRepository` routes format 1 pages through coordinated Markdown writes and format 2 pages through revision-checked SQLite transactions. In format 1, Trash is a sidebar scope backed by `Removed Pages` Markdown files, outside the derived search index. Format 2 keeps page trash in SQLite while preserving existing file-backed trash entries. Repository operations list, restore, and permanently delete these files under coordinated access, checking content hashes and path containment. Restore moves bytes to an available Wiki path and rejects active UUID/title collisions; no vault schema change is required. `NoteCodec` handles lossless Markdown bodies and frontmatter. `BlockDocument` and `BlockDocumentCodec` represent rich block trees (including inline math and display math blocks) and their compatible Markdown/JSON envelope; `BlockMutation` owns structural operations independently of AppKit. `TeXMath`, `TeXMacro`, and `TeXMacroStore` parse and expand custom `\newcommand` macros (with 0 to 3 arguments) and render TeX expressions for inline and display math. `MarkdownService` analyzes links/tags (excluding code and math) and produces a Sendable preview model. `SQLiteSearchIndex` maintains rebuildable search/tag/backlink tables. `RecoveryStore` journals unsaved drafts outside the synced folder.

**NativeAuthentication** owns operation-specific macOS authentication attempts independently of VaultCore, ExternalAI and SwiftUI. `LocalNativeAuthenticator` creates one private `LAContext` per invocation, uses device-owner authentication with the system-password fallback and disables Touch ID reuse from prior attempts. Cancellation and native callbacks arbitrate one completion; cancellation invalidates the context and delayed callbacks cannot resume a completed attempt. Callers receive only success or finite cancelled/unavailable/failed errors, never a context, credential or reusable authorization grant. ExternalAI retains its own session authority and expiry; successful native authentication cannot automatically authorize a different operation. Hardware prompt and accessibility acceptance remain [pending](validation.md#native-authentication-device-acceptance).

**noema** owns the UI. `AppModel` runs on the main actor; storage/index work runs in separate actors, and parsing runs in detached tasks. `ContentView` arranges navigation and pages. `NativeTextViews` bridges read-only source text and attributed source previews. `RichArticleView` bridges the article editor; `BlockEditorCoordinator` synchronizes its value document with one native `ArticleTextView`, manages selection/commands and the shared undo manager, and publishes the complete body to the existing draft/autosave path. `BlockTextStorage` renders/captures rich runs without flattening collapsed descendants. `BlockCommands` owns slash matching/presentation and a nonactivating native suggestion panel constrained above or below the caret within the visible editor; `SemanticRegistry` owns semantic icons, accessible names, and optional statuses. Native drag sessions carry document-scoped block IDs and reorder sibling subtrees; explicit indent/outdent commands change parentage. `VaultWatcher` forwards file-presenter and recursive FSEvents notifications into debounced reconciliation, including changes from editors that do not coordinate their writes.

The `VaultRepository` and `SearchIndex` protocols are the seams for replacing storage/index implementations. The AppKit-independent asynchronous `BlockStore` protocol is implemented by the actor-owned `SQLiteBlockStore` for format 2 page persistence. The [block architecture and storage contract](contracts/block-editor.md#storage-decision-and-implementation-gate-edtblk01) specifies one authority per vault, local-only SQLite pages, and explicit staged migration. `SQLiteVaultMigration` verifies backup/imported documents before conditional manifest cutover; preserved Markdown is never scanned as a second page authority. Keep UI actions out of codecs, and keep filesystem work out of view bodies. SQLite connections stay in their owning actors; canonical page SQLite is a reviewed storage exception, while source originals and metadata keep the existing byte adapter.

The contextual right inspector (`UI.R1–UI.R7`) lives in `Sources/noema/Inspector`. `InspectorContext` resolves the active page or source only for an available vault; `InspectorState` owns visibility, applicable tab memory, and session-invalidated presentation caches. Pages expose Links, References, Tags, Properties, and Insights; sources expose References, Properties, and Insights. `SearchIndex.outgoingLinks(from:)` queries the existing indexed link table, and `AppModel.updateBacklinks()` guards incoming/outgoing results against stale selections and sessions. `LinksPresentationCache` (`UI.R.REM02`) indexes normalized titles and aliases once per relevant metadata change, caches target resolution by page and target sequence, and hydrates current records by UUID. It retains only metadata and IDs, checks title/alias membership without normalizing on unchanged renders, and purges on session reset. `InsightsPresentationCache` decodes the current body only when its page or body changes. Reference and tag mutations retain the existing `AppModel` save/lock gates.

`AppModel.open` and `unlockVault` resolve the app-local base from `FileManager.default.url(for: .applicationSupportDirectory, in: .userDomainMask, appropriateFor: nil, create: true)`, unless a test supplies `localStorageRoot`. Both append `KnowledgeVault/<vault UUID>/search.sqlite` for the index and `KnowledgeVault/<vault UUID>/Drafts/` for recovery. `RecoveryStore` names each JSON draft `<note UUID>.json`; SQLite's WAL mode can create `search.sqlite-wal` and `search.sqlite-shm` beside the database. The Application Support URL is runtime-dependent and can reside in the sandbox application container; `~/Library/Application Support/KnowledgeVault/` is an unsandboxed example rather than a fixed production path. The index is derived data; recovery drafts can be the only unsaved copy. Neither is moved into the portable vault or encrypted by session locking.

`VaultContentStore` defines a lower-level vault-owned byte boundary. `PlaintextVaultContentStore` scopes root access per synchronous operation, validates relative paths and rejects symlink ancestry again inside NSFileCoordinator access, and atomically writes unchanged plaintext. Writes require create-only or expected-byte replacement; moves/deletes require a current file or flat source-directory snapshot and reject unresolved cloud versions. Preconditions and mutations share one coordination window; separate calls are not a transaction, and arbitrary uncoordinated filesystem writers remain outside that guarantee. Missing cloud bytes request hydration and report unavailable. Typed errors leave recovery/conflict preservation policy with the repository. Wiki creation, scan cache misses, saves, trashed-page reads, and preserved conflict copies use this adapter. Source original/metadata reads, metadata updates, staged publication, and source trash/restore/deletion also use it. Source staging directories use coordinated create-only directory creation; publication requires the exact expected original/metadata snapshot. Imported reader and availability reads use the same byte seam, while external linked files retain separate bookmark-scoped coordinated reads. Directory snapshots refuse conflicted children, and source mutations recheck expected bytes inside coordination. The repository retains NoteCodec, identity/alias validation, content hashes, scan caching, and cloud-version preservation policy; expected-byte replacement catches changes between the initial read and coordinated write. Manifest reads/create-only writes, structural directory creation, page trash/restore/permanent deletion, legacy trash migration, and retention ledger reads/expected-byte writes also use the adapter. A competing retention ledger write aborts expiration before any deletion. New-vault staging initializes canonical contents through the same repository/adapter; its parent-folder staging creation, publication move, and failed-staging cleanup remain separate because they are outside the eventual vault root. Discovery/enumeration, resource probes, provider hydration, and OS-owned conflict-version reads/resolution remain repository responsibilities. RecoveryStore and SQLiteSearchIndex remain separate app-local stores. RecoveryStore atomically journals unsaved JSON and removes decoded drafts only through explicit lifecycle actions. Listing isolates per-entry read, decode and identity errors, returning valid drafts alongside damaged-entry filenames and errors without modifying their original bytes. AppModel keeps damaged entries visible in recovery controls across open/unlock, while locked sessions clear their presentation and reject journal access. A new save targeting an existing damaged draft first renames that file to a unique preservation entry; removal of a damaged file through the decoded-draft API is refused. SQLiteSearchIndex owns its connection and WAL/SHM lifecycle inside its actor; its database is derived and rebuildable. Neither store belongs in the canonical content adapter. The format 1 adapter, external linked-file access, recovery journal and derived index keep their existing boundaries; format 2 page database ownership is described above.

Linked sources use optional `linkedBookmark` data in source metadata (source layout remains unchanged). The bookmark is generated with `securityScopeAllowOnlyReadAccess`; repository scanning resolves it and reads the external original under coordinated access, releasing the security scope afterward. These records have metadata only, with no in-vault original; the checksum records capture-time bytes, while subsequent linked reads accept external changes. Existing imported records retain checksum enforcement. File imports enforce a 2,000,000-byte maximum in the repository as well as the picker. UTF-8 text/Markdown/HTML provide searchable bodies; binary originals have empty derived text and retain byte checksums. Older app versions cannot read binary sources. Folder additions are rejected; the picker accepts at most five files per batch and rejects an excessive selection before creating records. Existing records from past folder additions remain readable. Before publication, repository additions inspect existing metadata under coordinated reads and reject matching original checksums across source modes or the same resolved linked file path. AppModel catches each selected file independently and accumulates named failures while continuing the batch. No filename-only match or persisted schema change is introduced. External files are never written by this path. Bookmarks are machine/app-specific; earlier app versions report linked records as unavailable rather than modifying them. Valid linked metadata remains visible with an empty derived body and transient availability issue when its original cannot be read. On-demand availability checks use coordinated reads and security scopes off the main actor, verify imported checksums, and never write source metadata. AppModel owns a serial queue and session-only results, cleared on vault switching. Refresh reloads linked content; the vault watcher does not watch external paths. Sources uses a navigation sidebar and table, with a resizable metadata/AI-summary inspector to the right when a row is selected. Selection is local UI state; double-click and Open Preview retain the separate native reader behavior. `SourceReader` owns native read-only NSTextView or QLPreviewView windows, retains security scope for their lifetime, and releases it when closed. Reader loading verifies in-vault checksums and uses coordinated reads off the main actor.

Source metadata optionally records `aiSummary` and `fileSize`, derived from canonical bytes during scanning for older records. `AppModel` owns a single serial source-title queue, exposes pending row IDs and completed/total progress, and clears pending work on vault changes. Files are published in the table before inference. Text/HTML/Markdown and PDFKit-extracted PDF text feed the existing on-device topic-title generator. Source inference uses the exact article `pageTitle` method and the same block-document normalization; HTML markup is stripped before normalization. For each queued file, separate on-device sessions generate the article-rule topic title and a concise summary concurrently from the same extracted content (at most the first 6,000 characters). Both results persist in one coordinated metadata write; empty summaries and stale prior summaries reject the write. Manual renames preserve the existing summary. No summary is rendered in the table; legacy metadata without `aiSummary` remains readable. The context menu and metadata inspector share provider-selected Summarize/Regenerate actions. Explicit on-device summaries extract text off the main actor from an exact repository source snapshot and publish through the same conditional publication API as cloud summaries; independent metadata/summary/original changes reject publication. Explicit enrichment generates the summary and validated classification together and publishes them in one conditional metadata write. Per-source progress disables duplicate requests, vault generation tokens discard earlier-vault results, and coordinated metadata writes preserve the display title and reject stale summaries/renames/deletions. Existing summaries remain visible until replacement succeeds. Context-menu rename changes only metadata and suppresses the queued AI result. Source deletion coordinates the UUID directory, rejects stale metadata, mutated imported bytes, symlinked directories/metadata, and unresolved conflicts. Linked deletions remove only vault records; imported deletions move the stored original and metadata to recoverable trash after explicit confirmation. Neither path recreates a deleted record. Repository title updates coordinate metadata writes, reject stale identity/title/checksum/bookmark/path values, and preserve original names and bytes. Queue errors retain original titles and surface a notice. Search is reconciled after successful renames. The local source-title queue stays on-device; no physical original-file rename is introduced.

Source-to-page AI creation reuses source text extraction and the on-device model actor. AppModel tracks in-flight source IDs and vault generation tokens, saves the current editor before navigation, and opens the generated article for editing. The repository creates the page and its initial source UUID reference in one format-aware page publication after checking the source still exists and its captured content matches; no intermediate unlinked page is published. Format 2 commits page metadata and blocks in one SQLite transaction; this does not transactionally reserve the separately file-backed source.

Page provenance is an ordered `sources` UUID sequence in format 1 frontmatter or format 2 SQLite page metadata; absent fields mean no references. Both inspectors derive their many-to-many relationship from pages. Repository updates use format-aware, revision-checked page saves, preserve bodies/original source bytes, and reject locked pages. Source relationship changes do not themselves change either supported vault format; legacy Markdown readers preserve this field as unknown YAML but do not expose it. Deleted/unavailable sources retain their UUID references until explicitly removed.

## AI provider preferences and explicit actions

`AIProviderPreferences` stores versioned global provider intent and overrides for Content enrichment, Title suggestions and Page creation. Page/source summaries share one preference. Legacy page-summary overrides win, followed by source-summary and retired LCC overrides; migration removes the independent classification setting without changing stored artifacts. Missing, malformed and future versions fail closed to on-device intent. Automatic source processing stays local regardless of preferences; a provider choice grants no submission or authentication authority.

`AppModel` captures the selected provider/client before asynchronous work. Explicit enrichment generates summary and classification together, filling only unset initial titles; regeneration preserves title/body. Both providers compose source/topic/URL drafts for review. Standalone title suggestions retain reviewed, conditional acceptance. The shared summary controls explain coupled classification; the Properties inspector exposes read-only classification metadata. See the unified contract below for publication, consent and acquisition boundaries.

`AISummaryPresentation` shares commands, progress, cancellation, copy and provenance across page/source/inspector views. OpenAI preflight inspects credential status without content dispatch. Required consent uses expanded exact-text disclosure for unauthenticated authority and compact disclosure only for a precise live authenticated lease. The global policy can authorize subsequent explicit submissions, but every inference still uses a fresh request-bound receipt and live gateway authentication/publication checks.

Person, Place and Concept identities, independent Question/Definition objects,

and SemanticStore; no additional connection or block-text authority is introduced.

also requires semanticAnnotationsV1. Manifest, database identity and capability
checks agree before admission; fresh staging is explicit, with no upgrade on open.

SemanticPageEdit provides verified UTF-16/grapheme-safe editing, structural edits,
undo and identity-safe page/block duplication with independent annotations and
copied anchored objects. Use these semantic APIs for object-aware duplication;
legacy document projections retain conservative unresolved copy provenance.
Schema-5 annotations have one relational authority. Inline document extensions are
load/export projections; unchanged whole-block anchors, exact edits and lifecycle

Production creation defaults, authority-changing migration, native tagging UI,
complete archives, device/accessibility and crash-durability gates remain separate
STOR02B/03 work. No AI extraction, inference or additional concrete types is added.

## Identity and evolution

Vault creation uses an application-owned SwiftUI sheet; NSOpenPanel selects only an existing parent. AppModel retains security-scoped parent access through off-main-actor creation and opening/bookmarking the child. FileVaultRepository.createNewVault validates the name and parent capabilities, stages the complete v1 plaintext structure beside its destination, and publishes it by a coordinated same-parent move without merging an occupied folder. Failed initialization/publication removes only positively observed empty owned staging; nonempty partial or completed vault contents are retained for recovery. Encryption intent stays transient: UI, AppModel, and repository gates reject encrypted requests before creation. The setup sheet exposes encryption as a disabled, off-state future capability and offers only explicitly confirmed plaintext creation. Optional access authentication is an independent per-Mac preference registered for the new UUID before first open; that open authenticates before loading content. Recovery keys, encryption metadata and encrypted indexing remain unavailable until cryptographic storage is implemented and tested together.

Trash combines SQLite page records and file-backed pages/sources without tabs.
Format 2 page Trash uses revision-checked `pages.trashed/trashed_at` transitions;
restore retains identity and blocks, while permanent deletion is a checked database
transaction. File-backed entries use `Removed Pages` rather than the externally
cleared `.Trash` name. Source deletion moves the complete UUID directory into a
collision-safe `.source` entry; linked external originals are never touched.
Restore rejects occupied identities/titles and duplicate sources. Timestamped
file entries, SQLite removal times and the coordinated `Trash Retention.json`
ledger enforce 15-day retention, with a full grace period for undated entries.
Damaged/unreadable/conflicted entries remain visible or preserved, with individual
errors; only readable safe snapshots authorize file deletion. Legacy `.Trash`
Markdown migration coordinates moves without rewriting content. AppModel
serializes actions, validates vault-generation results and refreshes derived state.
These current mechanisms do not establish SQLite ownership of source Trash or
conflict disposition; that explicit transition belongs to STOR.02.

New wiki pages and sources get UUIDs. A plain external Markdown page gets a deterministic temporary identity derived from vault UUID and relative path; that identity is persisted on first app save. Moving such a page externally before its first save changes its temporary identity. Persisted IDs survive moves. App title changes add aliases and retain stable filenames.

Vault manifests have an explicit format version. Reject unsupported versions instead of silently rewriting data. Preserve unknown frontmatter fields for future extensions. Canonical page authority is format 1 Markdown or format 2 SQLite, selected once by the manifest; source and preservation files retain their separate current authority. Search projections can be rebuilt, while recovery and conflicts may be unique data. Format 1 edited pages and Noema Markdown exports contain an independently versioned JSON envelope in a trailing HTML comment, guarded by a readable-body checksum. External text wins over stale metadata during Markdown decode/import; the old payload remains recoverable. Future envelope versions are read-only. Format 2 ignores preserved/exported Wiki files until explicit revision-checked import and does not require external Markdown editing. Search, tags, word count, and previews omit the metadata envelope. See `contracts/block-editor.md` for compatibility details. The NoemaTheme environment maps shared NoemaBrand palette roles to UI colors. Persisted `noema.theme` and `noema.theme.fullPalette` defaults select System or a light/dark palette, applied throughout the app or as an accent only. System and accent-only surfaces use dynamic AppKit semantic colors. Native selection and focus remain platform-managed; theme changes rerender attributed editor content without resetting selection or undo. Identity exports retain the default Midnight Iris tokens. The native theme dropdown uses shared, observable main-actor ThemePreviewState for transient highlights. Theme modifiers prefer this preview over persisted defaults; closing the menu commits only an explicit selection and otherwise restores the stored preference.

## Future extension constraints

- **Semantic retrieval:** derive heading-based sections with note/source UUID, heading path, content hash, and text. Store embeddings in local derived storage. Recompute changed sections, and label whether a passage is a source or a personal interpretation.
- **LLM context:** retrieve relevant passages, then apply the selected model’s tokenizer and context budget. Include compact identity/provenance metadata; do not replace the original text with a model’s token stream or generated summary.
- **Additional importers:** put PDF/web extraction behind an importer service; retain the original and treat extracted text as derived content. Extend source schema deliberately.
- **Mobile:** share VaultCore, build a separate UI, and test coordinated edits across platforms before claiming sync compatibility.

Start with one extension at a time. There is no application server, vector store, or runtime plugin system in v1. Explicit OpenAI summaries use the restricted ExternalAI module described below. `OnDeviceSummary` uses Apple Foundation Models asynchronously in a dedicated actor. Summaries use existing semantic block metadata (`summary`, `extra.aiGenerated`) without a schema version change. The native SwiftUI summary is rendered above the editable document; the binding retains it across edits. Generation only applies to the same unchanged, unlocked page and vault.

Automatic titles share the Foundation Models actor. AppModel tracks newly created placeholder titles in memory and finalizes them at navigation/lifecycle save boundaries, saving content before inference. Per-page background tasks save captured page snapshots through coordinated repository writes without requiring selection or focus. Stale hashes, deleted/locked pages, and changed active editors reject results; quit awaits pending tasks. NaturalLanguage detection chooses the article language with system preference fallback; Foundation Markdown parsing strips output formatting. Results require unchanged vault and page content; normal repository saves retain filenames and aliases. No persisted format changes.

Explicit Save Page (⌘S) and finishing editing register blank/Untitled placeholder pages for naming even after reopening. Other lifecycle triggers retain session-local eligibility.

URL captures use VaultCore WebSourceFetcher for HTTP(S) validation, uncached GET requests, status/type checks, a 20-second request timeout, and a bounded 2 MB response stream. FileVaultRepository publishes original response bytes and metadata through the existing staging/coordinated import path. Optional `isURLSource` and `webAvailabilityIssue` metadata distinguish URL captures from pasted/imported sources with origin links; absent fields preserve existing behavior, source layout is unchanged in both supported vault modes, and older readers ignore the new fields. AppModel imports at most five nonempty lines with independent error handling and feeds successes into the existing on-device naming/summary queue. URL availability checks refetch without changing canonical bytes, title, or summary; coordinated metadata updates persist archived/unavailable status and clear it on recovery. Search/scanning still derives content from the captured original.

The sandboxed app now permits outbound network connections. Its App Transport Security policy permits HTTP for explicitly entered source URLs, alongside HTTPS. Source captures feed the existing on-device inference path; capture itself never submits to an external AI provider.

Topic-page creation uses VaultCore WebTopicResearch to query Bing's public RSS search, parse ranked HTTP(S) result links, and fetch up to three readable HTML/text pages among the first five using the existing bounded WebSourceFetcher. Async research supplies bounded untrusted text to the selected composition provider, with request-bound authorization and the configured submission confirmation policy for OpenAI. AppModel guards duplicate requests and stale vault/editor contexts, saves current editing first, and exposes a transient draft with numbered web citations and application-supplied result URLs. Explicit review publishes through coordinated page creation. Empty/blocked search or entirely unreadable results fail without publication; there is no general-knowledge fallback. See the unified enrichment contract below.

Page editing locks use a dedicated repository operation through the existing coordinated, stale-checked save path, preserving `updatedAt` for the lock metadata write. Pending editor content is saved first through the ordinary content save. AppModel serializes saves and suppresses duplicate per-page lock requests, publishing the returned persisted snapshot only after success. Sidebar ordering derives directly from content timestamps, with no presentation holds or delayed move feedback. Lock state remains optional format 1 frontmatter or format 2 page metadata, without changing either format; editing locks provide accidental-edit prevention, without encryption or authentication.

## Storage adapter replacement contract (D01.6)

See `contracts/storage-boundary.md` for the final canonical-access inventory and permitted I/O exceptions. The build and test wrappers run `scripts/check-storage-boundary.py`; exceptional access is explicitly reviewed in `scripts/storage-io-exceptions.json`.

A future encrypted byte implementation would implement `VaultContentStore` and return logical plaintext bytes to the existing codecs/repository. Canonical SQLite additionally requires separately reviewed encrypted connection/key construction; a byte adapter cannot encrypt a live database by replacing its files. Expected-byte writes and file/directory snapshots must compare logical contents while retaining coordinated physical access, atomic publication, containment/symlink checks, create-only refusal, stale/conflict preservation, hydration errors and file-presenter notifications. It must retain the selected root's security-scoped capability. Separate protocol calls remain separate operations, without an implied transaction.

`VaultStorageProvider` is the explicit construction policy: repository open selects one store (or accepts the existing direct injection), retains it as a nonisolated Sendable dependency, and AppModel passes that same store to readers, availability checks and summary extraction. These consumers require an explicit store and cannot default to plaintext. AppModel retains its provider across vault switches and passes it to new-vault creation; creation selects a store for its temporary staging root, and opening the published root selects a fresh store rather than reusing one bound to the moved staging path. The construction guard permits runtime plaintext adapter construction only in the provider. Session authorization belongs to the separate `VaultSessionManager` / `VaultAccessGate` layer. Discovery currently sees physical filenames/resource values, so a design that hides names or changes layout also needs a deliberate discovery seam. Imported Quick Look previews receive disposable copies of adapter-validated bytes rather than canonical URLs. SourcePreviewDirectory owns the temporary noema-source-previews-v1 directory, with private UUID snapshot directories and payloads plus a versioned ownership marker holding a process lease. Reader close, errors and vault switching attempt removal; launch cleanup examines at most 128 immediate children and removes only validated, unlocked snapshot files without recursive deletion. Active readers, invalid markers, extra contents, symlinks, unrelated temporary files and unmarked legacy noema-preview-UUID directories are preserved. Cleanup errors can leave copies for later attempts. Linked previews retain external URL/security-scope behavior. This is ordinary lifecycle cleanup, not secure deletion or encryption; preview copies remain plaintext app-local temporary files and future encrypted storage needs a separate confidentiality policy. OS conflict-version bytes must be interpreted through the chosen format before logical preservation. Encrypted-preview confidentiality and encrypted conflict-version interpretation remain future design requirements.

Plaintext Markdown format 1 and explicit local SQLite page format 2 are supported; neither provides at-rest encryption. Any future encryption requires explicit format negotiation and opt-in migration, independent key/recovery design, and a policy for plaintext recovery drafts, SQLite copies/WAL, previews and external originals. It must test existing plaintext/legacy vault compatibility, interrupted publication, stale writes, cloud conflicts and two-Mac synchronization before sign-off. No crypto stubs, key fields, encrypted adapter or claim of at-rest protection is added here.

`VaultSessionManager` in `VaultCore` owns the standalone six-state vault session state machine (`closed`, `opening`, `open`, `locking`, `locked`, `unlocking`), typed transition errors (`VaultSessionError`), session identity (`VaultSession` with vault UUID, canonical root URL, and monotonic `generation`/`epoch`), serialized transitions, duplicate-request coalescing, cancellation rollback, and read-only `AsyncStream<VaultSessionState>` observation independent of `AppModel` and SwiftUI. `VaultAccessGate`, `VaultSessionLease`, `VaultAccessError`, and `GatedVaultContentStore` connect `VaultSessionManager` to the `VaultContentStore` and `FileVaultRepository` boundaries: every protected read and write requires a valid lease matching the active open session's UUID, vault ID, canonical root, and generation, revalidated synchronously when repository actor methods and adapter I/O actually execute (including after async suspension points) so queued or in-flight work crossing a lock or vault-switch boundary is rejected. `VaultLockAdmissionBarrier`, `VaultAdmittedOperation`, `VaultOperationRegistration`, `VaultOperationRegistrySnapshot`, and `VaultOperationAdmissionError` share the gate's atomic lock: transitioning `open → locking` atomically closes the admission barrier to new protected operations while retaining previously admitted operations in the registry, allowing scoped admitted work to finish draining, handling concurrent lock callers, task cancellation, and `deinit`-guarded abandoned registrations, and awaiting in-flight completion before transitioning to `locked`. `VaultSaveQuiescenceCoordinator`, `VaultQuiescentOperationContext`, `VaultPendingEditorState`, `VaultQuiescenceReport`, and `VaultQuiescenceError` coordinate safe quiescence of in-flight saves, autosaves, LCC metadata updates, and source imports/downloads during `locking`: operations distinguish pre-commit work (which can be cooperatively cancelled, journaling unsaved page edits to `RecoveryStore` and cleaning up `.import-*` staging directories) from the durable commit window (which finishes uninterrupted so committed writes remain recognized), while unrecoverable quiescence or recovery failures abort the lock transition and keep the session in `open` without falsely publishing `locked`. `VaultStaleResultGuard`, `VaultCompletionTicket`, `VaultCompletionKind`, `VaultStaleCompletionReason`, and `VaultStaleCompletionError` validate asynchronous completions against the active session identity (`sessionID`, `vaultID`, `root`), monotonic `generation` epoch, UI generation token, target entity ID, and captured content before publishing search, preview, source loading/availability, indexing/refresh, or AI-processing results into `AppModel`, `SQLiteSearchIndex`, or `SourceReader`, even when cooperative task cancellation is ignored. `FileVaultRepository.inspectManifest(at:contentStore:storageProvider:)` and `FileVaultRepository.preflightOpen(root:create:storageProvider:)` keep `vault.json` manifest and directory safety inspection outside the protected content API so destination vaults are validated before tearing down an active or locked session; if destination preflight fails, the previous vault remains intact, whereas initialization failures after transition begins close an owned newly opened session or return an owned unlock to its prior locked identity. Rejected rollback is surfaced and reconciled to the actual central state; stale resources are not published. `RecoveryStore` (`open`, `store`, `remove`, `drafts`), `SQLiteSearchIndex`, `SourceReader` (both imported and linked source reads and window presentation), and `AppModel.sourceSummaryContent` enforce `VaultAccessGate` / `VaultSessionLease` validation, while post-drain recovery draft journaling during lock quiescence executes within a registered quiescence scope. Session locking and leases implement **application-level access revocation and lifecycle isolation**, not cryptographic protection: canonical vault files and page SQLite/WAL/SHM, app-local SQLite FTS5 indexes, recovery draft JSON files, disposable Quick Look preview files, and external linked originals remain plaintext on disk until Phase 3 cryptographic storage is implemented.

The [plaintext vault access authentication contract](contracts/vault-access-authentication.md) governs optional native admission in `VaultSessionManager` for every supported production open/unlock route. It binds a private single-use attempt to root, vault UUID, action, lifecycle state/generation and policy revision while retaining the closed/locked phase. Production authentication/policy dependencies are fixed; closure loaders and substituted dependencies are internal test seams. Settings authenticate both preference directions, and permission recovery follows the same unlock boundary. App-local UserDefaults preferences and all vault-related files remain readable to filesystem/process access; this feature provides casual application access control without encryption.

Lifecycle actions in `AppModel` reject overlapping open/lock/unlock/close requests and retain manager failures as typed `sessionTransitionErrors` alongside their UI message. A failed close preserves existing resources; successful close requires the central `.closed` state before resources and bookmarks are discarded. Lock completion verifies the vault identity and generation, and open/unlock publish initialized resources only while their session still owns the gate. Rollback failures are presented with the initialization error and reconcile to the actual central state. State observations ignore obsolete emissions and purge loaded resources when a new open session has a different lease. Coalesced manager close callers await the shared state commit and receive the same typed failure. Recovery construction requires a gate and an explicit valid lease; ungated fixtures use a separate internal initializer.

Implementation and acceptance are tracked separately in the [milestone evidence matrix](validation.md#d02-evidence-matrix), with links to named session, gate, quiescence, AppModel, and stale-completion tests. Those tests exercise specified interleavings and injected failures, not every possible task schedule. The durable commit window prevents cooperative lifecycle cancellation from interrupting a canonical operation; it does not establish process-crash, power-loss, or real provider atomic-write fault guarantees. `NSFileCoordinator` covers cooperating access, while separate storage calls remain separate operations. A local save acknowledgment does not establish iCloud upload or arrival on another device; the [two-Mac acceptance procedure](validation.md#two-mac-acceptance-procedure) remains required for transport sign-off. Phase 3 encryption, key management, and protection of all plaintext copies remain future work.


## Native workspace window and pane ownership

The singleton `Window("Noema", id: "main")` owns one `AppModel`. Native titled chrome
owns standard controls and top safe areas; no traffic-light coordinate enforcer or
workspace titlebar overlap is permitted. Global controls live in one native toolbar;
document editing controls remain with the document heading. Toolbar and menu actions
share guarded `AppModel.performWorkspaceCommand`, with lifecycle admission reserved
before queuing. Activation/termination still use existing save/recovery/session hooks.

`AppModel.searchText` owns the query. Search mode, category scope and explicit
idle/searching/results/failure status share the existing `SidebarSearchResults`;
full-vault search retains SQLite FTS and semantic snapshot search, while Quick Open
filters page/source titles and page aliases. Query publication checks a search
revision alongside the existing session completion ticket, so superseded queries,
mode/scope changes, selection, catalog/editor mutations and vault revocation cannot
publish older results. Mutations invalidate synchronously, before view refresh.
The 120 ms debounce remains. Library rows and semantic catalogs refresh by catalog,
editor and scope revisions; row construction runs off the main actor rather than
rebuilding the library on each query. Toolbar expansion, responder restoration, keyboard
selection and the anchored results popover belong to `ToolbarSearchView`; compact
windows place its field inside the popover. The first eight results share a route
to the explicit full results view. Entry and category refinement preserve the open
document and library scope; result navigation uses the existing save-before-select
path, including semantic block targets. Admitted workspace navigation dismisses
transient search views; consent/review sheets block search focus commands. Native
input composition retains arrow, Return and Escape handling. Search does not
require a visible sidebar.

`WorkspaceWindowTitle` derives identity from existing metadata and the central gate,
without reading source bodies. Welcome uses Noema; library/page/primary-source identity
and vault subtitle are available only to an authorized open session. Locking/locked/
unlocking presentation must withhold previous private document names immediately,
including before asynchronous observations catch up. Keep full accessibility labels
while native titlebar truncation handles long names. Sources row selection remains
inspector state and does not become a primary document title.

`HSplitView` remains because the center alternates between library/native Table and
editor, while inspector availability is independent. `WorkspacePaneState` persists
sidebar/inspector intent and widths separately from effective visibility. Narrow
windows/context loss can suppress panes without erasing intent; widening restores
requested panes. Search is independent of sidebar visibility; an explicit inspector
request prioritizes the inspector when one outer pane fits. Session resets clear transient tabs/caches while retaining visibility/widths.

Center minimums are 420 pt for documents and 520 pt for Sources; sidebar min/initial/
max is 190/265/320 pt, and inspector is 280/340/420 pt. Native dividers own dragging.
The split probe preserves controller holding priorities and the SwiftUI delegate,
restores widths through `setPosition` only for pane arrangement/center-minimum changes,
and records widths only from native resize notifications during mouse dragging.
Window resizing must not overwrite preferred widths or animate heavy document/Table
layout; pane/title/toolbar evaluation must not decode source bodies or rebuild the
Sources metadata/status presentation bridge. Inspector respects native top safe area.

`WindowGeometryProfile` separates saved welcome and workspace frames: defaults
680×480 and 1280×820 content points, minimums 560×400 and 720×540. Restoration clamps
to current usable displays, including disconnected/offscreen display changes. Opening
retains the prior profile; open/locking uses workspace, closed/locked/unlocking uses
welcome. Full-screen transitions defer frame changes and preserve saved geometry.
Window probes operate only on their attached main window, never whichever auxiliary
window is key. About (660×560), Settings, source readers and nonactivating caret panels
retain their existing chrome/focus/security-scope/preview cleanup ownership. Geometry
restoration must not open a vault twice or introduce a second lifecycle controller.

See [native window acceptance](validation.md#native-window-acceptance) for source tests,
scoped performed UI checks and remaining interaction/accessibility acceptance.

## External AI and content enrichment

`ExternalAI` retains the authenticated credential/session/gateway boundary in the [external AI contract](contracts/external-ai.md). `ExternalAIEnrichment` is the common bounded result for explicit page/source enrichment and reviewed page composition. The OpenAI gateway sends one strict Responses inference for all requested artifacts; the native provider uses one Foundation Models JSON response, validated by the same strict artifact parser. Initial enrichment may fill an unset title; regeneration preserves title and body. Read-only typed LCC metadata resolves code, level and caption through the local verified vocabulary. Legacy frontmatter/source JSON and provenance remain readable until explicit enrichment replaces them.

`SummaryPublication` encodes complete summary/classification/title updates into one conditional adapter write, with captured byte/change-token, lease and synchronous publication-guard checks. Related provenance carries a fresh generation identity independent of request authority. Page composition reuses source extraction, `WebTopicResearch` and `WebSourceFetcher`, adds references locally, and retains only a transient draft until review. A create-only write validates the draft permit and any linked source snapshot. URL capture retention is a separate source transaction; failed page creation preserves an already imported capture.

Global consent policy lives in `ExternalAIService`, separate from provider configuration and Keychain authentication. Always ask fails closed; once-per-session grants bind the exact unlocked lease; never ask requires explicit Settings selection. Every explicitly invoked operation still receives a fresh request-bound receipt and gateway authentication. Lock/switch/relaunch revoke the session grant. URL host/address/redirect policy rejects local/private destinations; DNS prechecks do not pin network endpoints. Device, provider, accessibility and durability limitations remain in [validation](validation.md).

Admission checks and canonical writes are separate synchronous steps. A write already admitted immediately before revocation/editor invalidation can complete concurrently; holding the authorization lock across gated storage would invert lock order and deadlock. No asynchronous gap is permitted between final validation and that write. External linked originals can also change after their final read; metadata compare-and-swap cannot make separate externally owned files transactional. These boundaries and the remaining in-process/cancellation/provider-retention risks are described in [external AI contract](contracts/external-ai.md). Device authentication and notification delivery require the [manual acceptance gate](validation.md#d02a-device-acceptance-checklist).

## AI activity history

`AIActivityRecorder` shares one lazy application-level `SQLiteAIActivityStore` across local callers and the OpenAI gateway. The database is independent of vault search indexes. A caller allocates one logical ID, begins immediately before local inference or when capturing a cloud submission, and finalizes after publication or proposal generation. Unified enrichment and reviewed page composition each retain one record. Helper inference calls share that ID; proposal acceptance/dismissal updates its outcome without creating another inference record. Gateway observations carry only bounded dispatch counts and validated optional token usage. Dispatch is observed at actual transport resume; asynchronous persistence runs outside authorization locks and is followed by the existing authority/cancellation checks. Connection validation has its own targetless record.

Schema v2 preserves v1 history and retention settings while adding page composition. The store owns versioned schema initialization, interrupted-operation reconciliation, idempotent finalization, indexed bounded queries and retention. Settings history uses latest-request snapshot ownership to reject delayed reads after clearing, pruning or a newer refresh, and explicit refresh with 50-row pages, with provider/action/status/outcome/date/current-vault filters. Current titles are resolved only from the accessible vault's loaded metadata; stale and inaccessible targets cannot navigate. Metadata export is bounded to 1,000 records. Cost calculation uses an injected versioned catalogue keyed by model and effective dates, including cached input rates; the default unpriced catalogue displays unknown cost rather than inventing charges. See the [activity contract](contracts/external-ai.md#activity-history) and [storage ownership](contracts/storage-boundary.md).
